# H11 spike: forking a worker across machines, sandbox included

**Verdict: H11 passes.** A headless Claude Code worker can be checkpointed on one machine and forked
on another, with its working directory, in about 7 seconds. Its 645 MB sandbox becomes a 266 MB
snapshot. The bar was under 2 minutes and under 1 GB (v2.2 §11, H11). The recommended method is a
tar plus zstd snapshot of the working directory, shipped together with the session transcript and
its side files. Claude Code can declare `supports_checkpoint: true` under the conditions in
[Harness limitations](#harness-limitations-and-supports_checkpoint).

Issue: #24. Reproduce with `python3 spikes/checkpoint/run.py` (see
[spikes/checkpoint/README.md](../../spikes/checkpoint/README.md)). Raw numbers are in
`spikes/checkpoint/results/`.

## What was measured

- **Machines.** Two Docker containers, A and B, with separate volumes, talking only over a network
  whose rate is capped at 100 MB/s (about 0.8 Gbit/s) by `curl --limit-rate`. Both ran on one
  Docker Desktop host (10 CPUs, Apple silicon).
- **Harness.** Claude Code 2.1.308, the real CLI in `-p` (headless) mode. The model API was a
  scripted mock (`ANTHROPIC_BASE_URL`), so no tokens were spent and every model reply is instant.
  The mock fills its tool calls from the conversation it receives, which lets the run prove that
  the resumed history reached the model.
- **Sandbox.** A clone of this repository standing in for testbed problem A, which has not landed
  yet. The worker made commits, deleted a tracked file, and left staged, unstaged and untracked
  edits. It also built a uv venv with the simulator's dependencies (simpy, numpy, pandas, scipy,
  matplotlib: 307 MB) and wrote 300 MB of sweep outputs: CSV job traces, float arrays, compressed
  results and a run log. In total that is 645 MB in 7,630 paths.
- **Conversation.** A first session with one tool call that reads a random nonce. Its output is
  large enough that Claude Code saved it to a side file. The transcript is 207 KB.
- **Timer.** From the start of the checkpoint on A to the first tool call of the fork on B,
  including Claude Code's start-up. Model latency is not included (see [Caveats](#caveats)).
- **Correctness, checked for every run:**
  - Files: every path's kind, mode, size and SHA-256 on B must match A.
  - Git: HEAD, branch, status, staged and unstaged diffs and the local config must match.
  - Conversation: the fork recalls the nonce from history, and its first model request carries
    the earlier goal and tool result.
  - Prompt cache: that first request must repeat the source's last request as a prefix.

## Results

Medians of 3 runs (the range of the total is in brackets). Snapshot is the sandbox part; the
conversation adds 0.08 MB to every approach.

| Approach | Total (s) | Checkpoint (s) | Transfer (s) | Restore (s) | Resume (s) | Snapshot (MB) | Files and git match | Passes H11 |
|---|---|---|---|---|---|---|---|---|
| (a) tar plus zstd of the working directory | 7.3 [6.9–8.8] | 2.0 | 2.6 | 1.6 | 0.7 | 266 | yes | yes |
| (b) git bundle plus a tar of untracked files | 7.3 [7.1–14.0] | 2.0 | 2.7 | 1.7 | 0.8 | 266 | yes | yes |
| (c) overlayfs upper directory | 7.4 [6.2–21.0] | 1.7 | 2.7 | 1.8 | 0.9 | 266 | yes | yes |
| (d) command log plus replay | 39.9 [28.9–52.5] | 0.0 | 0.0 | 39.0 | 0.7 | 0.002 | no | no |
| (a) without the venv, rebuilt from `uv pip freeze` | 17.7 [14.3–21.7] | 2.5 | 1.9 | 12.1 | 1.1 | 188 | yes, except bytecode caches | yes |

The slow ends of the ranges all come from the third repetition, when the shared host was busy; no
approach was consistently slower than the others.

**Where the bar bites.** One more run with 1.5 GB of outputs (a 1.85 GB sandbox, one repetition)
gave a 940 MB snapshot and a 24.6 s fork with tar plus zstd. Replay took 122 s. So with outputs
like these, **the 1 GB size cap is reached at a sandbox of about 1.9 GB, long before the 2-minute
cap**. At 100 MB/s the time grows by roughly 25 s per GB of snapshot.

## The conversation

### What has to travel

For a session `<id>` run in working directory `<cwd>`, Claude Code keeps everything under
`~/.claude/projects/<cwd with / replaced by ->/`:

- `<id>.jsonl`: the transcript. It holds every message, tool call, tool result and per-turn usage,
  plus internal records (request shapes, attachments, cost state).
- `<id>/`: side files. Tool outputs too large for the context are saved to `<id>/tool-results/` and
  referenced from the transcript **by absolute path**. Subagent transcripts also live here.
- `memory/`: the project's automatic memory, shared by all sessions in that directory.

Nothing else is needed. The target machine had its own fresh `~/.claude.json`, and the
`session-env/` folder stayed empty. Packed with zstd, the three items came to 78 KB.

What the transcript does **not** contain, so the harness must store it in the checkpoint record and
pass it again at resume: the command-line flags (allowed tools, `--mcp-config`, model, appended
system prompt, permission mode). The transcript does record which MCP servers were connected or
failed, and their tool names, as history, but not their configuration. The MCP servers are
"pointers to tool state" in D5's terms; the herd's tool server is reachable from any machine, so
passing the same `--mcp-config` is enough.

### Resume and fork

`claude -p --resume <id> --fork-session "<new goal>"` worked on machine B with only those files
copied:

- It starts a new session ID and leaves the source transcript unchanged.
- The first model request carried the whole earlier conversation. The fork recalled the nonce from
  a tool result that existed only in that history.
- `--resume` finds the session in any project folder, so a different working directory does not
  stop the resume. But tool inputs and side-file references in the history are absolute paths. The
  target should therefore use **the same home directory and the same sandbox path** as the source
  (here `/home/node` and `/work/repo`). The executor controls both.
- **Prompt cache.** The fork's first request repeated the source's last request exactly as a prefix:
  same tools, same system prompt, same messages. So a fork within the cache lifetime (5 minutes, or
  1 hour with the longer cache) pays only for the new turn. That matches D5's assumption. This held
  for all 15 forks.
- **A copy taken mid-turn still resumes.** In a separate probe, the transcript was copied while a
  tool call was still running. Claude Code then added its own result for that call, "Tool call
  interrupted: the session ended before this call's result was recorded, so its outcome is
  unknown", and the fork went on. So a crashed worker (D35) can be resumed, but the in-flight tool
  result is lost.

### Context usage (feeds D77 and W1-08)

Every assistant entry in the transcript carries the API's `usage`. Context in use is
`input_tokens + cache_read_input_tokens + cache_creation_input_tokens` of the last assistant entry.
These numbers matched what the API returned, exactly, for every turn. The window size is not in the
transcript. It is in the `-p --output-format json` result, as `modelUsage.<model>.contextWindow`
(1,000,000 for the default model in 2.1.308). The executor can therefore record usage at
checkpoint time without any API call, and D5's "prefer checkpoints under 60%" is computable.

### Claude Agent SDK (for H12)

The Python `claude-agent-sdk` 0.2.172 bundles the same CLI (2.1.308, 280 MB). Its options include
`resume`, `fork_session` and `session_id`. It also has a `SessionStore` interface: the SDK mirrors
transcript entries into external storage as the session runs, and on `resume` it rebuilds the
session from the store in a temporary config directory. `import_session_to_store` copies an
existing local session in.

The spike forked the same session through the SDK with the transcript **only** in a small
directory-backed store (36 KB packed). The fork recalled the nonce. Two gaps:

- **Side files do not travel.** The store keeps transcript entries only, so `<id>/tool-results/`
  was missing on the target. A forked agent that tries to reopen a large earlier output would find
  nothing. The harness has to ship that folder itself.
- **The system prompt differs by one line.** Claude Code's attribution header names its entry point
  (`sdk-cli` for the CLI, `sdk-py` for the Python SDK). Whether the API counts that line in the
  cache key is not known. The safe rule is to fork through the same entry point as the source.

## The sandbox

- **(a) tar plus zstd** of the whole working directory (`zstd -T0 -3`). The simplest method, needs
  nothing on the target, and was exact. Compression took 645 MB to 266 MB: the venv went from
  307 MB to about 78 MB, and the repository plus outputs from 338 MB to 188 MB.
- **(b) git bundle plus untracked tar.** No smaller than (a), because almost all the bytes are
  untracked: the venv and the outputs. It needs a clone of the base commit on the target and more
  steps (stash, bundle, fetch, switch, apply). It was exact only because the local `.git/config` was
  copied along; git alone does not carry it.
- **(c) overlayfs upper directory.** The same size again, and exact, deletions included (overlay
  stores them as whiteout files). It needs privileged mounts and a byte-identical base layer on the
  target. In production this is the container runtime's own snapshot (for example `docker commit`
  of the worker container), which would also capture changes outside the working directory.
- **(d) command log plus replay.** The checkpoint is tiny, but restore re-runs the whole session, so
  its cost grows with how long the worker has run. Here that was 40 s for a 27 s session; a real
  worker runs simulations for hours. It is also not exact:
  - the run log differs, because it contains wall-clock times and a random run ID;
  - every bytecode file differs;
  - the replayed commits get new hashes, so commit IDs the agent saw in its history no longer exist.

  The log must also record the content of every file the agent wrote with its Write and Edit tools.
  These are not shell commands.
- **(a) without the venv.** A 30% smaller snapshot, but restore downloads packages again (from PyPI
  here, with a cold cache) and was the slowest of the exact methods. Only the bytecode caches
  differ. It is worth it only on a slow link.

**Recommendation.** Use (a), a tar plus zstd of the whole working directory, in the same checkpoint
record as the conversation files and the harness's launch flags. On a slower link, stream it
(tar into zstd into the upload, and the reverse on the target) so compression, transfer and
extraction overlap. Consider excluding rebuildable folders only if links turn out to be the
bottleneck.

## Harness limitations and supports_checkpoint

`supports_checkpoint` can be true for Claude Code headless, with these conditions:

1. **`export_state`** packs `<id>.jsonl`, the `<id>/` folder and `memory/`, plus the launch flags.
   **`import_state`** unpacks them under the same home directory and runs
   `claude -p --resume <id> --fork-session` from the same sandbox path.
2. **Checkpoint between turns where possible.** Claude Code appends to the transcript while a turn
   runs. A copy taken mid-turn still resumes, but the running tool call's result is replaced by an
   "outcome unknown" note. Running processes are not captured (there is no process snapshot): a
   simulation running at checkpoint time has to be restarted by the fork.
3. **Pin the Claude Code version.** The transcript format is internal and has many record types.
   Source and target must run the same version, which the worker image already pins.
4. **Same paths on both machines** (see [Resume and fork](#resume-and-fork)).
5. Files outside the working directory, such as `~/.cache` or packages installed with `--user`, are
   not in an (a) snapshot. Workers should keep their state inside the sandbox.

## Caveats

- **No real model.** The resume time (about 0.7 s) is Claude Code's start-up plus an instant mock
  reply. With a real model, add the time to the first tool call of one turn. With the prompt cache
  warm, that is usually a few seconds, which leaves the total far under 2 minutes. This was not
  measured.
- **One host.** A and B shared the host's disks and CPUs, and the network was a capped virtual
  link. Transfer time is size divided by rate: at 25 MB/s (200 Mbit/s) the 266 MB snapshot would
  take about 11 s instead of 2.6 s. If the checkpoint goes through object storage without
  streaming, the transfer happens twice (upload, then download).
- **Stand-in content.** The repository is this repo, not problem A, and the outputs are synthetic
  but mixed to resemble a scheduling sweep. The transcript is short (2 turns). Real transcripts
  reach several MB, which adds well under a second at these rates.

## Fallback

Not needed: H11 passes. If sandboxes later outgrow the bar (several GB of outputs that must travel),
the order of retreat is:

1. Exclude rebuildable folders (venvs, caches) from the snapshot, as in the last table row.
2. Keep large outputs out of the sandbox, in the blackboard or an artifact store, and pass pointers.
3. Use D5's own fallback, the conversation plus command-log replay, accepting that the replayed
   sandbox differs as shown under (d).
