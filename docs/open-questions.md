## Before the first real run (Appendix C)

| Which problem does the PoC use? What are the judge's latency, daily quota and concurrency? Is there a holdout? | It sets the ladder, the quota and whether local proxies are needed. The system itself is validated on testbed problems A and B, not on a real problem. A real problem keeps artificial scarcity (latency ≥ 10 minutes, 2 runs per hour for the whole herd) even if its judge is fast | 2026-11-05, decided by Claude at @minyi-tang's delegation. Until H1 is done, `examples/prompt_optimization` is the standing real problem (model-graded judge, about 1 minute per run, 1000 runs a day declared, the audit set as holdout). It is a demonstration, not evidence for any hypothesis, so it carries no artificial scarcity. The first real project is chosen after the comparison on problem A (one-page §5 step 5) and then takes the spec's floor: latency at least 10 minutes and 2 runs per hour for the whole herd. #117's code-repository example is built as its issue describes |
| Preregistration: the minimum effect worth detecting, N = 5 or 10 workers, the number of independent runs, and eval machine-hours per arm | A comparison that wasn't preregistered can't be judged (D42, D72) | 2026-11-05, decided by Claude at @minyi-tang's delegation; **provisional until the pilot, and sealed only by @minyi-tang's signature on the preregistration file** (D72). Arms: S2 (Planner off) against B1+M, gated; S1 as a diagnostic arm, not gated. N = 5 workers per arm. One run is 24 hours on problem A (TB§7 runs its control arms for 24 hours). Budget per arm per run is what the slow-eval service enforces: 48 worker submissions at 2 per hour, 16 Integrator remeasures, 10 `holdout_run` checks, 5 verdict repeats; the fast tier is unlimited. Machine-hours are runs times the cost per run measured during #124's A/A remeasures, the same for every arm (D42 rule 2). Minimum meaningful effect: S2's share of available gain captured on `holdout_verdict` exceeds B1+M's by 10 percentage points. Runs: the smallest n with power ≥ 0.8 at that effect, σ_run taken as 1.5 times the pilot's, at least 3 and at most 6 batches; if n is above 6 the comparison runs as exploratory and says so, and the effect is not raised afterwards. Test: one-sided paired t-test, α = 0.05, paired by batch. Acceptance rule: default (1 standard error), as in `params.yaml`. Exclusion: a whole batch is dropped and rerun only for an infrastructure failure (the service or the model gateway down for more than 30 minutes in any arm), decided before the verdict split is opened |
| Which harness and model id (one model for every role)? What are the API's concurrency and rate limits? | They decide the hook mechanism and the checkpoint format, and how many agents can run at once | 2026-10-22, the model: it is the user's configuration and the herd puts no limit on it; GPT 6.1 Sol, Opus 5.5 and Astra Max are all available. The Copilot harness logs the model each session ran on and warns only when `allowed_models` is configured and a call ran outside it. Harness: Copilot CLI first (#48), Claude Code in #41. Concurrency and rate limits (2026-11-05, decided by Claude at @minyi-tang's delegation): the herd configures no limit. Within a batch every arm runs at the same time (D72), so the peak is 2 arms of 5 worker sessions; problem A's judge makes no model calls. Before the pilot, load the gateway at that peak for 10 minutes. If it throttles, drop S1 from the batch; if it still throttles, run the arms back to back on the same day and record that as a deviation in the preregistration |

Slots at N = 5: `order` 2, the others 1 each, because the ordering hook carries both backfill and fair-share, the pair precheck row 4 sets against each other. The deployment copy's `params.yaml` gets these values; the checked-in folder stays a draft |
| Access to the cluster repo; which services exist (KV, object storage, git, image registry, database); worker pod size and maximum count | They decide which adapters to build (Wave 3) | 2026-11-05, decided by Claude at @minyi-tang's delegation. | Each source's `trust` and `readable_by` (D45). Is the private store a separate repo or a bucket? How are worker credentials isolated? | They decide whether definitions live on the blackboard or in the private store (D63). Credentials as built: a per-session read token for the worker's served view, no worker push (D68), and only the eval service reads private material. The values go into the deployment copy that is signed, not into the checked-in draft |
